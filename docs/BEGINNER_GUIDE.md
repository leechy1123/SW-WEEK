# 15분 만에 경험하는 웹 보안

## 준비 · 2분

Python 3.10 이상을 준비합니다. 프로젝트 폴더에서 `python app.py`로 실행하고 http://127.0.0.1:8000 을 여세요. Python이 설치되어 있지 않으면 [Python 공식 다운로드](https://www.python.org/downloads/)에서 설치하세요. Windows에서는 설치 프로그램의 PATH 추가 옵션을 선택하면 터미널에서 실행하기 편합니다.

브라우저는 질문하는 쪽, 서버는 답하는 쪽입니다. 이 프로젝트는 여러분의 컴퓨터가 두 역할을 모두 합니다. 서버가 켜져 있는 동안만 실습 URL이 열립니다.

## A01 · 내 열쇠가 남의 문도 열어요 · 3분

1. ‘직접 실습해 보기’를 누릅니다. ‘앨리스’ 사용자를 유지하세요.
2. ‘1번 글 보기’ → 내 글이 보입니다. HTTP 200은 요청이 성공했다는 뜻입니다.
3. ‘2번 글 보기’ → 밥의 비공개 메모까지 보입니다. 여기가 문제입니다.
4. ‘수정 후로 전환’을 누르고 같은 동작을 반복합니다. 내 글은 보이지만 밥의 글은 HTTP 403으로 거절됩니다.

이유: 로그인 확인은 ‘누구인가?’, 권한 확인은 ‘이 정보를 볼 수 있는가?’입니다. 두 가지 모두 필요합니다. 서버가 글의 `owner`와 `current_user`를 비교하면 다른 사람의 글을 차단할 수 있습니다.

확인 질문: 브라우저에서 2번 글 버튼을 숨기기만 해도 해결될까요? **아니요. 주소를 직접 요청할 수 있으므로 서버의 검사가 필요합니다.**

## A02 · 오류 안내가 내부 정보를 말해요 · 3분

1. 수정 전에서 ‘정상 응답 보기’를 누르면 HTTP 200이 나옵니다.
2. ‘상세 오류 보기’를 누르면 Traceback과 파일 경로가 나옵니다.
3. 수정 후에서 같은 버튼을 누르면 일반적인 안내만 나옵니다.

이유: 개발자에게는 도움이 되는 상세 오류가 외부 사용자에게는 불필요한 내부 정보일 수 있습니다. 화면에 보여줄 정보와 내부 기록을 구분해야 합니다.

확인 질문: 수정 후에도 HTTP 500이면 실패한 걸까요? **아니요. 이 실습은 일부러 오류를 발생시킵니다. 확인할 것은 내부 정보가 숨겨졌는지입니다.** 일반 서비스에서는 오류 원인도 해결하고 보호된 로그에 기록해야 합니다.

## A05 · 검색어가 검색 조건을 바꿔요 · 3분

1. 수정 전에서 ‘정상 검색 · 노트’를 누르면 상품 1개가 나옵니다.
2. ‘참 조건 입력 · 1=1’을 누르면 상품 3개가 나옵니다.
3. ‘거짓 조건 입력 · 1=2’를 누르면 상품 0개가 나옵니다.
4. 수정 후에서는 두 테스트 입력 모두 0개, 정상 ‘노트’ 검색은 계속 1개입니다.

왜 달라질까요? 수정 전 SQL은 입력을 문자열로 붙입니다. 입력에 포함된 따옴표가 원래의 문자열을 닫고, 뒤의 조건이 검색 명령의 일부가 됩니다. 수정 후에는 `?` 자리에 값을 따로 전달해서 입력 전체를 하나의 상품명으로 다룹니다.

확인 질문: 따옴표를 무조건 삭제하면 해결될까요? **정상 데이터까지 망가뜨릴 수 있습니다. 명령과 데이터를 분리하는 매개변수 바인딩을 사용하세요.**

## 비교하고 발표하기 · 4분

1. 대시보드에서 권한 확인란을 체크하고 ‘수정 전후 한 번에 비교’를 누릅니다.
2. 수정 전 3건 발견 → 수정 후 3건 통과인지 확인합니다.
3. 결과를 펼쳐 요청 경로, 상태, 실제 응답을 확인합니다.
4. ‘정상 기능 유지’도 확인합니다. 모든 요청을 차단하는 것은 좋은 수정이 아닙니다.
5. ‘결과 저장’으로 JSON 파일을 저장합니다. 이 파일은 문서 편집기나 VS Code로 읽을 수 있습니다.

발표 예시: ‘A01에서 앨리스가 밥의 글을 볼 수 있었습니다. 서버에 소유자 검사를 추가하자 본인 글 조회는 유지하면서 남의 글은 403으로 차단됐습니다. 같은 요청을 두 버전에 보내 검증했습니다.’

## 다음 단계 · 코드를 직접 수정하기

`lab.py` 상단의 REPAIR 옵션을 한 개씩 True로 바꾸면 수정 전 환경에도 보호 로직이 적용됩니다. 코드를 바꾼 뒤에는 반드시 서버를 재시작하세요. 한 단계씩 바꾸며 통과 항목이 늘어나는지 확인하면 됩니다.

더 배우려면 `read_post`, `error_page`, `search_products`의 조건문을 읽고, `scanner.py`의 `evaluate`에서 어떤 증거로 판정하는지 따라가 보세요. 이 프로젝트의 주석은 복잡한 최적화보다 이해하기 쉬운 흐름에 초점을 두었습니다.

## 자주 막히는 부분

| 증상 | 해결 |
| --- | --- |
| python 명령을 찾을 수 없음 | Windows는 py -3 app.py 시도. Python 미설치라면 먼저 설치 |
| 주소가 열리지 않음 | 서버 터미널이 켜져 있는지 확인. 파일을 직접 열지 말고 출력된 HTTP 주소 사용 |
| 이미 사용 중인 포트 | python app.py --port 8001 실행 |
| 코드가 반영되지 않음 | 파일 저장 → Ctrl+C → 다시 실행 → 진단 다시 시작 |
| 진단할 수 없는 URL | 대시보드의 수정 전/수정 후 버튼으로 정확한 로컬 URL 선택 |
| 수정 전이 이미 통과함 | lab.py의 REPAIR 옵션이 True인지 확인 |
| 미확인으로 표시됨 | 정상 기능이 깨지거나 예상하지 못한 응답임. 통과로 해석하지 말고 코드 복구 후 재진단 |
| 다른 컴퓨터에서 URL 접속 실패 | 로컬 전용 주소임. 각자 프로젝트를 실행해야 함 |
